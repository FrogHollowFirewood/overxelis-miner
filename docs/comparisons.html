OverXelis Miner (OXM): early local observations from the maintainer’s AMD Ryzen Threadripper PRO 7995WX desktop, using 192 requested CPU threads. These are different test sessions, not a controlled six-miner tournament.

Read the scope before the percentages. A difference between local displays or counters does not establish a difference in accepted work, earnings, or performance on other hardware. Follow-up: accepted work and recovered logs

Added 29 October 2026 (UTC). These observations extend the original records below; they do not replace them or establish a controlled ranking.

HydraX now has an accepted-share trial

The second HydraX v3.4.5 session ran from 03:34:03.958 to 03:44:22.469 UTC: about 10 minutes 19 seconds. It recorded 11 accepted shares and zero rejections. Thirty displayed rates averaged 19.242 kH/s (range 19.18–19.42); the final five averaged 19.186 kH/s. The miner requested 192 threads and reported 4 KB fallback pages.

This is enough to document working pool submissions and the displayed speed of this tested configuration. It is not enough to establish a matched performance advantage: OXM used 2 MiB huge pages, the software reports differ, and a complete fee-cycle or longer-run payout comparison was not established. The earlier no-accepted-share result remains below as the initial trial, not the latest status.

OXM: hashing speed is not the downtime-inclusive average

The latest completed desktop beta.2 session had an uninterrupted first interval of approximately 44 minutes 52 seconds, ending with a 110.707 kH/s session average. That supports a live running rate close to the retained 110.615 kH/s development reference. It is only about 0.08% higher, not evidence of a substantially new speed level.

The whole session lasted about 71 minutes 34 seconds, with 52 minutes 43 seconds of recorded active user work and about 18 minutes 51 seconds not active. Its final all-time average was 81.730 kH/s. An active-time-only reconstruction is approximately 110.969 kH/s, but uses rounded display values and second-resolution timestamps, not an exact stored counter boundary.

The final recovery interval included short readings up to 113.595 kH/s. Those do not replace the longer reference. The session ended with 293 accepted, zero rejected, and 30 unresolved submissions; unresolved means the outcome was not confirmed, not that the pool rejected the share. No developer-fee window occurred. Recovery reliability and unknown submissions still need attention.

Why the rounded numbers look different

The maintainer described the latest short trials as about 96 kH/s for hoo_cpu and 18 kH/s for HydraX. Against the 110.615 kH/s OXM reference, those rounded inputs yield approximately 15.2% and 514.5% higher displayed rates. The table instead uses the more precise retained readings. Neither calculation makes HydraX’s unvalidated run a fair accepted-throughput comparison.

We report miner-by-miner values rather than one speed range across all six projects. The available evidence supports specific, qualified observations—not a blanket ranking. The follow-up above adds historical SRBMiner-MULTI and cpuminer-opt-supr observations. TNN-Miner still has no usable rate in the retained run. None is a matched OXM comparison.

Version and memory context

The hoo_cpu trial used v1.4.3, while its official download page listed v1.4.24 when checked. A separate attempt with the newer release did not produce a qualified hashrate result in the reviewed records. The older observation is not presented as the current release’s performance. HydraX’s 4 KB memory mode differs from OXM’s huge-page configuration. That difference must not be hidden in a headline.

What a fair comparison needs

Record the CPU and operating system, exact miner versions and binary identities, compiler/build flags, requested and actual thread placement, actual memory mode, clock and power settings, and temperatures. Use the same work source and pool where practical. Run miners sequentially without competing CPU workloads, and balance run order to reduce heating and order effects.

Choose warmup and measurement durations before testing. Keep all planned runs, including failures, and repeat each configuration. Distinguish local completed-hash rates from pool estimates and report accepted, rejected, stale, and unresolved work. Compare accepted difficulty-weighted work over sufficient time; share counts alone are not comparable when difficulties differ.

For earnings or fee-efficiency claims, cover complete fee cycles and include reconnection overhead and user-only accepted work. Publish per-run results, variation, exclusions, and limitations. Never convert a startup peak, a crash, or a zero-share trial into proof of a competitor’s maximum speed.
