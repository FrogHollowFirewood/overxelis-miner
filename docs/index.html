01 / The approach

Know what your
miner is doing.

Clear settings, visible fees, and correctness checks before hashing. No promises of guaranteed returns or a universal speed advantage.

01

Choose your destination

Enter your own XELIS payout address, compatible Stratum pool, and worker name. No wallet seed, custody, or deposit.

02

See both sides of the fee

Separate USER and FEE modes show where work is going. The terminal reports accepted shares and active-time accounting.

03

Test without a hidden service

Run the miner in the foreground and stop with Ctrl+C. It does not install an autostart service or change your clocks.

Development update · 9 November 2026

Beta.5 Kryptex trial

Archived result from the beta.5 testing period.

In a trial that ended November 9, 2026, a beta.5 development build ran on Kryptex for 33 hours, 31 minutes, 18 seconds on an AMD Threadripper PRO 7995WX with 192 huge-page workers. The miner displayed a session average of 124.060 kH/s. The run recorded 13,911 accepted user shares, 137 accepted fee shares, zero rejected shares and 13 unresolved submissions during connection interruptions. The CPU peaked at 83.875 °C, below the 85 °C guard. All workers closed normally after a requested stop.

The rate comes from the miner’s session display. The run did not capture a completed-hash counter window or CPU package power. It does not establish a matched speed gain or qualify the 140 kH/s target.

The source preview is based on the tested development kernel and warm-handoff runtime. The public package was rebuilt with its own version metadata. The 33-hour trial predates that public rebuild.

The separate Stage 3 scratchpad patch remains in development. Its offline checks passed, and desktop qualification and a matched Kryptex test are pending.

02 / Earlier beta.4 hotfix · 6 November 2026

Measured work.
Clear conditions.

The beta.4 logged hour, short GPU-on counter measurements and unpatched hour use separate evidence and methods.

Beta.4 preview 2 crash fix. The earlier beta.4 source preview 1 can stop with an integer divide-by-zero fault, shown by the shell as “floating point exception.” Preview 2 checks the selected production kernel before that division, consumes the failed nonce, and excludes it from completed work and share submission. The first failing input is retained in the native runtime for diagnostics; the public launcher does not automatically save it to disk. The cause of the original zero intermediate value remains unverified because that input was not saved. Read the fix, qualification and limits.

Development hotfix logged hour · 6 November 2026

60 minutes 27.49 seconds after warmup · 192 huge-page workers · 119.739756 kH/s mean of 361 rounded local displays; sampled minimum 119.517, maximum 119.978 kH/s. The measured interval accepted 444 USER shares; the full session accepted 450, with zero rejected or unresolved displayed. All native workers closed normally after a requested stop.

This is logged continuity evidence from the development hotfix, whose native library is byte-identical to the qualified public preview-2 build. The launcher retained its earlier preview-1 banner. Raw hash-counter boundaries and a monotonic interval were not saved; native drops/undefined skips, GPU activity, cooling and temperatures were not recorded for this session. This is not an exact-counter hour, a full fee cycle or a 120 kH/s guarantee.

No invented hash

A zero round modulus is rejected before division. That nonce is consumed, is not counted as completed work, and cannot enter the submission queue.

REAL POOL WORK

25 and 28 accepted shares

Two approximately 191-second measured windows after warmup, with zero rejected, unresolved or queue-dropped work. These are short observations, not a soak test.

CORRECTNESS CHECKS

1,031 inputs · four C paths

Saved Rust answers replayed, complete scratchpads compared, and 192 actual huge-page workers verified. Forced-zero tests exercised 1, 24, 32 and 192 workers.

Scope: zero rejected, unresolved or queue-dropped work was reported in these short measurements. Saved Rust answers were replayed through four C implementations for 1,031 inputs, full scratchpads were compared, and 192 actual huge-page workers were verified. Forced-zero guard tests exercised 1, 24, 32 and 192 workers. Rust was not newly executed. These checks support the observed selected-kernel repair and normal hash behavior; they do not establish long-term stability, broad hardware performance, an exact-counter hotfix hour, a fee-cycle pass or a general 120 kH/s guarantee.

The production selected kernel uses the checked path. Reference and experimental kernels retain their earlier zero-modulus behavior; the legacy void selected API deliberately traps on failure. The hotfix does not define a new consensus hash for an undefined input. Capturing and replaying a naturally failing input remains necessary to distinguish a reference edge case, an optimization discrepancy or a transient computation fault.

04 / Get started

From source to
your first share.

Download and verify first. Follow the complete guide for dependencies, build checks, memory modes, and troubleshooting.

01

Verify, then extract

Download the archive and its checksum file. Stop if the checksum fails. A checksum is not a publisher signature.

sha256sum --check SHA256SUMS-v1.1.1.txt && \
tar -xzf OverXelis-Miner-1.1.1-source.tar.gz && \
cd OverXelis-Miner-1.1.1
02

Build and qualify

Stop other CPU miners normally. The build command uses GCC from your PATH. The miner fetches no compiler. Do not bypass a failed hash check.

python3 -I -B build_public.py --compiler gcc && \
python3 -I -B qualify_public.py && \
bash run.sh --self-test
03

Add your settings

The terminal wizard asks for your public payout address, pool, worker name, threads, and memory mode. No private keys.

bash run.sh --configure && \
bash run.sh --check
04

Start deliberately. Stop anytime.

The flag acknowledges the disclosed 1% scheduled developer fee. Keep the terminal open. Ctrl+C stops this miner.

bash run.sh --config config.json --accept-dev-fee

New to source builds? Start with the complete installation guide, not a copied command alone.

07 / What to expect

Honest answers.
Useful testing.

Is OverXelis officially part of XELIS?

No. OverXelis Miner (OXM) is an independent community project. It is not affiliated with or endorsed by the XELIS project, Slixe, or Kryptex. XELIS is the network this software mines.

With gratitude: thank you to Slixe (GitHub profile, opens in a new tab) for creating XELIS and for his development work, and to the wider XELIS contributor community. We deeply value the project’s work on privacy, open participation, and programmable digital money. This acknowledgment expresses our appreciation—not an endorsement of OXM.

What do our recorded tests show?

See recorded runtime and hashrate for 192, 32 and 24 threads ↗

The earlier result below is one session within that total.

The Kryptex trial lasted 33 hours, 31 minutes, 18 seconds on an AMD Threadripper PRO 7995WX with 192 huge-page workers. The miner displayed a session average of 124.060 kH/s. Kryptex accepted 13,911 user shares and 137 fee shares. The miner recorded zero rejected shares and 13 unresolved submissions during connection interruptions. The trial recorded a session-display rate. A completed-hash counter window and CPU package power were unavailable. A matched speed gain and the 140 kH/s target remain unverified. Read the beta.5 trial and the earlier beta.4 validation.

Can I use Windows, a GPU, or an ARM computer?

This download is a Linux x86-64 CPU source release. It does not include a Windows executable, a macOS build, an ARM build, or a GPU miner. Do not assume compatibility with untested environments.

Will opening this page use my CPU to mine?

No. This is a static project website. Mining begins only when you deliberately run the installed miner on your own computer. There is no browser miner, remote activation, or automatic service installation.

What still needs validation?

The separate Stage 3 scratchpad patch remains in development. Its offline checks passed, and desktop qualification and a matched Kryptex test are pending. A sustained 140 kH/s result, package-power comparison and broader hardware qualification remain open. Read the current scope.

Why do local and pool hashrates differ?

The console counts local completed hashes. The pool estimates useful work from submitted shares. Short samples, connection gaps, stale shares, and fee allocation can affect the comparison. Report the measurement window and accepted/rejected counts.

What happens if I see an error or a security warning?

Stop on invalid hashes or checksum errors. Preserve redacted logs. Do not blindly disable security software. The native workers retain bounded nonce tracking instead of beta.2’s 32,768-entry cache stop. Duplicate and lower nonce protection persists across jobs, reconnects and USER/FEE changes. This correction does not establish long-soak reliability.
